# TidyMind

A Windows desktop app (WPF, .NET 10, `net10.0-windows10.0.19041.0`) for personal organizing. Everything stays on the PC; the only network use is the optional update check (see Updates). A *memory* is one area of life, either a **project memory** (projects with tasks, notes, files, plus a to-do list) or a **collection memory** (items such as clothing or vehicles with fields and logs). Also: Home dashboard, Calendar, Day Plan, Reminders (Windows notifications), Quick Notes, global search, export (Excel/Word/PDF), backup/restore, a guided tour. UI languages: English, Hungarian, Serbian (Latin).

## Layout
- `TidyMind/` the app (one project, flat): windows/views (`*.xaml` + `.xaml.cs`), data layer (`*Store.cs`, `*Service.cs`, `Profile.cs`, `Project.cs`, `Entity.cs`, …), `Loc.cs`/`Msg.cs`/`Strings*.resx` (localization).
- `installer/` Inno Setup script `TidyMind.iss`, `build-installer.ps1`, `publish-release.ps1`, `release-notes/<version>.md`, `TERMS.txt`, `PRIVACY.txt`. Output goes to `dist/` (git-ignored).
- `tests/Harness/` console harness that starts the real app (`App.OnStartup`) against a **temp** data folder and drives it.
- `noslop-reports/` review notes, screenshots, glossary. Git-ignored, never committed.

## Data storage
- Everything lives in `%LOCALAPPDATA%\TidyMind` (`AppPaths.DataFolder`, `AppPaths.Data(name)`); never build paths from the working directory.
- Top-level files: `profiles.json` (the memories), `reminders.json`, `calendar.json`, `quicktodos.json`, `quicknotes.txt`, `dayplan.json`, `settings.json`; image/attachment folders (`CardImages`, `BackgroundImages`, `EntityImages`, `Attachments`); logs `error.log`, `reminders.log`, `updates.log` (always English).
- Each memory has its own folder `Memories\<Id>\` (named by `Profile.Id`, see `MemoryFiles`): `projects.json` or `entities.json`, `tabs.json`, `todos.json`.
- Writes go through `AtomicFile` (temp file, then replace). Model classes carry `[JsonExtensionData]` so fields from other versions survive a save.
- Unreadable file: the `TryLoad` pattern. Say "couldn't read", never save over it (views are read-only then).
- Migrations (`LegacyDataMigration`, `MemoryLayoutMigration`) never overwrite existing files.
- A new data type must also be covered by backup/restore (`DataBackup` zips the whole data folder and validates on restore), export (`ExportService`), and search (`SearchIndexBuilder`).
- Stored values are culture-invariant (dates `yyyy-MM-dd`, numbers with `.`). A restore keeps the current language (`DataBackup.KeepLanguage`).

## Shared helpers: reuse, don't duplicate
`TextSearch` (accent-insensitive matching) · `TextEditing`/`TextCopy` (inline editors, copy) · `IconButtonStyle`, `HoverIconButtonStyle`, `GhostButtonStyle`, `LinkButtonStyle`, `SegmentStyle`, `SearchBoxStyle`, `NoteInputStyle` (`App.xaml`) · `ImageCache`/`ImageStore`/`EntityImages` (pictures) · `AttachmentStore` · `EntityFiles` (an item's files, deleted only when no item uses them) · `EntityTypes` (field, section, record, tab and log definitions, `Values`, `Units`, `Currency`, `Expiry`, `Choices`) with `FieldEditor` (an input per field kind), `CellPanel` (equal columns that reflow), `LogEditor` · `CardEffects`, `DragReorder`, `SwatchRow` · selecting several and deleting them at once: `ItemSelection` (Ctrl/Shift/Ctrl+A/Esc/Delete, bulk menu; attach before an item's own click and drag handlers), `CardSelectionController` (adds the marquee on card grids), `SelectionLook`, `BulkDelete` (one confirmation, "and N more", kept-items report), `SelectionBar`; every list that deletes one item also deletes a selection through the same code · `AgendaMenus` · `TaskOrder` (the order of every checkbox task list) · the item window's pieces in `ItemSections.cs` (`ItemLook`, `FieldsSection`, `RecordRow`, `EditDialog`) and `ItemCompact.cs` (`CompactRecords`) · reminders: `ReminderManager`, `ReminderForm`, `ReminderActions` · Day Plan: `DayPlanStore`, `DayPlanBlock`, `DayPlanActions`, `DayPlanReminders`, `DayPlanTodos`, `DayPlanView`, `DayPlanBlockDialog`.

## Reminders
- Each reminder is one Task Scheduler task `TidyMind_Reminder_<Id>` running `TidyMind.exe --remind "<Id>"` (no UI) at its next time; repeating ones are re-registered after firing.
- `reminders.json` changes run under the named mutex `Local\TidyMind_Reminders` in `ReminderManager`. The app itself is single-instance (`Local\TidyMind_SingleInstance`).
- Toast: sent under the AppUserModelID `TidyMind.App` (`App.UserModelId`, must equal the installer's `MyAppUserModelId`; the Start Menu shortcut carries it). `ToastNotifier.Setting` is only logged, never a gate (Windows 10 throws 0x80070490 there before the first toast). If the toast fails, `ReminderPopups` shows the reminder in the open app, or in a window of the `--remind` process. The text uses the saved language (`Loc.Initialize` runs before `--remind` is handled).
- Settings → Send test notification: one toast from the app, one through a real one-off task (`TidyMind_NotificationTest_*`, `--test-notification <token>`); results in reminders.log.
- The uninstaller runs `TidyMind.exe --remove-reminder-tasks`; the app also repairs missing/stale tasks at start (`RepairTasksInBackground`).

## Installer
- Build: `powershell -ExecutionPolicy Bypass -File installer\build-installer.ps1` → `dist\TidyMind-Setup-<version>.exe` (needs Inno Setup 6).
- **Never change `AppId`** in `TidyMind.iss` (upgrades and uninstall find the install by it).
- Per-user install, no admin. Uninstall keeps `%LOCALAPPDATA%\TidyMind` unless the user answers Yes to the "delete data?" prompt (silent uninstall always keeps it).
- Wizard languages: English + Hungarian only, following the Windows UI language. Inno Setup ships no Serbian file, so Serbian is not offered. TERMS.txt/PRIVACY.txt are English only.

## Updates
- One version number: `<Version>` in `TidyMind.csproj`. The app reads it from the assembly (`Updates.CurrentVersion`, shown in Settings), `build-installer.ps1` passes it to Inno Setup, the installer is `TidyMind-Setup-<version>.exe`.
- Releases are installers in the public repo `Umbra-tech04/TidyMind-releases` (no source). Owner/repo are constants in one place: `UpdateEndpoints.ReleaseOwner`/`ReleaseRepo` (`publish-release.ps1` reads them from there). Each release: tag `v<version>`, assets `TidyMind-Setup-<version>.exe` and `TidyMind-Setup-<version>.exe.sha256` (`<hash>  <file name>`), notes = the release text (shown as plain text, cut at 4000 characters).
- The start-up request goes out from `App.OnStartup` right after the single-instance and migration steps (`Updates.BeginStartupCheck`, background), and `Updates.Start` takes up its answer. At start (`Updates.Start`, background, never blocks): old downloads deleted, the last update's outcome logged (and a message if it failed), then, only if `CheckForUpdates` isn't false, a check at every start (no daily limit; `LastUpdateCheck` in settings.json is only shown in Settings) and again 6 h after the last automatic one while the app runs (`RecheckIfDue`, looked at every 5 min): GET `api.github.com/repos/.../releases/latest`, 10 s timeout, User-Agent `TidyMind/<version>`, nothing else sent except `If-None-Match` with the ETag GitHub gave earlier in the same run (kept in memory only; a 304 reuses that answer). Drafts, pre-releases and non-`x.y.z` tags are ignored; only a strictly newer version is offered. Every failure is silent on the automatic check; Settings > Updates > Check now says it in words. Everything goes to `updates.log` (English, data folder, not in backups).
- A newer version found (automatic or Check now, not skipped) is `Updates.Available`: the sidebar's "Update available" button (`UpdateIndicator`, shown without taking focus) opens the same dialog any time and stays until the update is installed or that version skipped. The popup `UpdateDialog` opens when the main window is free (`IsIdle`: in front, no modal dialog or message box, no tour, no click/drag/open menu in progress, no key typed into a text box in the last 3 s; mouse moves and clicks never hold it back); a found update waits for that however long it takes (one waits, a newer find replaces it). Later = no popup until the next start (re-checks still update the button); Skip = `SkippedUpdate` until a newer one appears (the button goes too).
- Update now: `UpdateClient.DownloadAsync` → `%TEMP%\TidyMind-update\<name>.part`, renamed when complete, then size and SHA-256 checked on disk while the file is held open (others may read, nobody may change it) → `VerifiedInstaller`. Only `github.com/<owner>/<repo>/releases/download/...` and GitHub's asset hosts (`UpdateEndpoints.GitHubAssetHosts`), HTTPS only; redirects are followed by hand and checked. Then `Updates.Apply`: every other window closed the normal way (each saves). One that refuses: the dialog closes so the user can deal with it (a modal dialog disables every other window) and comes back when idle with the installer already checked. Then `pending.json` written, installer started with `/SILENT /SUPPRESSMSGBOXES /NORESTART /NOCANCEL /RELAUNCH=1 /LOG=...`, `Application.Shutdown()` (App.OnExit releases the single-instance mutex).
- Installer side (`TidyMind.iss`): with `/RELAUNCH=1`, `InitializeSetup` waits up to 60 s for the mutex to go, and `DeinitializeSetup` starts `{app}\TidyMind.exe` again: the new version, or the old one when setup failed and rolled back. A normal install keeps the "Launch TidyMind" checkbox. Same `{app}` folder, so reminder tasks keep their exe path; a task that ran during the install and failed is rescheduled by the start-up repair (`ReminderManager.IsHealthy`).
- Release: write `installer\release-notes\<version>.md`, raise `<Version>`, run `installer\publish-release.ps1 -DryRun`, then without `-DryRun` (needs `gh auth login`). Never run it without `-DryRun` unless the user asks.
- **Rules:** never change the AppId; never rename the releases repo, the tag form or the asset names without changing both the app (`UpdateEndpoints`, `UpdateRelease.InstallerName`) and `publish-release.ps1`, since installed copies only know the old ones. Never add a setting, argument or environment variable that redirects the production update check or download: the only other endpoints are made by the test harness (`Updates.Endpoints`, internal, `InternalsVisibleTo("Harness")`).

## Vehicle record
- Every collection item opens in `ItemWindow` (the same for every type; owner the main window, size in settings.json `ItemWindowWidth/Height`): `PictureHero` on top, a title block (what it is, name, `EntityTypes.Headline` facts and what comes due as chips, the actions), then the type's sections: a type with several tabs (`EntityTypes.Tabs`) gets an Overview and a list of pages beside the content (a dropdown above it when narrow), one tab (clothing) is a single page. Sections are edited in place, one at a time (`IInlineEdit`, `Gate`: `FieldsSection` for a section's fields, `CompactRecords` for a line of a compact list); a record or a log is edited in an `EditDialog`. Every change writes at once through the collection view (`Host.Save` = `CollectionView.Replace`: by Id, then `EntityFiles.DeleteUnreferenced` and `VehicleReminders.Follow`) and the page is drawn again from it. Esc empties the search, stops an edit (asks if changed), else closes; Left/Right browse pictures.
- **Switching pages changes the content and nothing else.** The page is one scrolling column (pictures, title block, page list, content), so a shorter page used to shrink the scroll extent and cut the offset back, moving everything above it. Now, with several pages, `Page.MinHeight` is the window's height (so any offset up to the page list's top stays valid) and the scroll bar is always shown (its coming and going never moves the column); `ScrollToBody` keeps the offset, or goes up to the page list's top if scrolled further down. All sections share one template (`ItemLook.Heading`, `HeadingMargin`, `FieldsMargin`, `SectionTop/HeadingBottom/SectionBottom`; the page title line is a fixed height): never set a section's margins by hand. Harness `items` measures it (`SwitchPages`).
- **Forms never run off the side.** Inputs live in `CellPanel` columns that reflow (`EditDialog.Inputs`, minimum column 220); every input must fit the narrowest column, so a number with a unit pair (kW + hp) is a `Grid` of two star-sized boxes (`FieldEditor.NumberWithUnit`), a file picker trims its name, the own-item row of a check list wraps. Harness `items` opens every form (each section's edit, every record dialog, every log, the item form) at 560, 760 and 1100 px in three languages and fails on any element WPF cuts at its slot (`CutOff`: the layout clip is narrower than the element) or text that doesn't fit.
- **No row hides its primary actions.** A record's row (`RecordRow`) shows Edit and Delete as small icons at its end (`ItemLook.RowAction`, shown on hover and keyboard focus, their room always kept); opening the row shows the other fields and what else the list adds (making a wheel set the mounted one, a part's moves). A row with nothing more to show has nothing to open. A compact list (`RecordDefinition.Compact`, now the garment's sizes) is a table with every line on view (`CompactRecords`): a column per field, the number named by `StepKey` with - / + that save at once and keep the keyboard on the button, Add and Edit open a line in the table itself (Enter saves, Esc leaves), Delete asks. The logs are tables with an Edit link in the heading; no other list expands to reach an action.
- Schema (`VehicleSchema`): `FieldDefinition` (kinds Text, Number with `Unit`/`Alternate` (hp from kW), Choice, Date, Flag, CheckList, LongText; a record's File, Specs and Pictures; `InForm` = also in the item form), `SectionDefinition`, `RecordDefinition` (a list of `EntityRecord`s; `Nested` = records under records, `RecordTree`, at most `RecordTree.MaxDepth` levels so the JSON always reads back; `CurrentKey` = the one in use, the mounted wheel set), `TabDefinition`, logs (Service, Fuel, Odometer). Tabs: Overview, Specs, Wheels & tyres (wheel sets), Fluids & parts (fluids, brakes, battery and bulbs, the parts outline: rows indented by depth with an arrow to open the ones that hold others, a part's moves in its opened row; "Start with the usual systems" = `PartsTemplate`, named in the current language once), Documents, Service & costs (the service log: entries newest first with a filter by kind (`FilterKey`), the costs per kind, per year and in all (`TotalKey`), then the fuel and odometer logs). The search box (`ItemSearch`, Ctrl+F, Esc clears) lists every field, record cell, spec and log row that matches; a click opens its tab and record. The window, form, search (`Describe`/`SearchText`), PDF/Word, Excel (typed cells, a sheet per record list) and transfer all go through it; never name a field in those places.
- Storage: the old typed fields stay (`VehicleKind`, `Plate`, `Year`, `OdometerKm`, `Color`, `Notes`); every new field is `Entity.Details[key]`, record lists `Entity.Records[key]` (each `EntityRecord`: `Id`, `Values`, optional `File` in Attachments/, `Pictures` in EntityImages/ (in `EntityFiles.Pictures`, so delete safety and transfer cover them), `Specs`, `Children`), all `WhenWritingNull`: an untouched vehicle is stored byte for byte as before, an older version keeps them as unknown fields. Values are invariant (`Values`); distances are in the vehicle's `OdometerUnit` (km/mi), money is a plain number shown with the `Currency` setting (Settings > General; empty = the Windows region's symbol).
- Documents (`VehicleDocuments`) are the deadlines (card line, Home, badges). Old `InsuranceExpires`/`InspectionExpires` are shown as documents (fixed Id per vehicle and type) without a write; storing the list sets both fields to the newest date of that type; an older version's edit of a field moves the newest such document. Never migrate them on read.
- Service log (`VehicleService`): entries of a kind (service, repair, modification, tax or fee, note) with date, odometer, work, place, cost, the parts fitted (a `Links` field: part Ids; saving sets each part's installed date and odometer through `RecordDefinition.Saved`, and a part's card lists the entries that name it) and the next due date and/or reading. The old `Logs["Service"]` rows show as entries without a write (fixed Ids); storing writes every entry back as such a row for older versions; a row an older version added shows as an entry of its own. Only the newest entry of each kind counts for its next due (`DueFrom = VehicleService.Latest`).
- What comes due is generic: `RecordDefinition.DueKey`/`RemindKey` (dates: `EntityTypes.Expiries`, documents and services) and `DueDistanceKey` (`EntityTypes.DistanceDues`: within `DistanceSoon` (1 000 of the vehicle's unit) of the manually updated odometer, or passed; shown in the app only: badges, Overview, the card line, Home). Transfer gives links and `CurrentKey` values the records' new Ids.
- A date that comes due with "remind" days (a document's, a service's next one) has one one-off reminder (Id = the record's, 09:00 that many days before; a day already past: the next 09:00 if still before the date). `VehicleReminders.Follow(before, after)` after every save, delete (one, a selection, a memory) and import; title = vehicle name, message empty and made when shown (`ShownMessage` with `DeadlineIndex`, `RecordDefinition.ReminderText`, used by the toast, Reminders and Home). Harness: `vehicle`.

## Item pictures (collection items)
- An item holds up to `EntityImages.MaxPictures` (20) pictures: `Entity.ImagePath` is the cover, `Entity.MoreImages` (written only when non-empty, so a one-picture item is stored exactly as before and an older version keeps the field in `ExtensionData`) the rest. Always go through `EntityImages` (`Names`, `SetNames`, `Cover`, `Apply`); files are copied into `EntityImages/` under new GUID names, as before. No migration: an old item simply has no `MoreImages`.
- A file is deleted only through `EntityImages.DeleteUnreferenced`, which looks at every collection's saved items (imported data can share a file) and deletes nothing if one of those files can't be read. Never `DeleteCopy` a picture an item may still hold (it is for copies made in a failed save).
- The item form (`EntityForm`) edits a list of `PictureSlot`s (stored name or picked file) and one `selectedPicture`, the single source of truth; `CollectionView` copies the picked ones in after Save (one that can't be copied is left out and named, the rest of the edit kept) and removes them again if the save fails. `PictureBrowser` (form and detail card) only draws what it is given: the selected picture large, previous/next arrows and Left/Right that only browse, a thumbnail strip (first = Cover); reordering is Move earlier/later, Make cover or a drag in the strip (form only), and the moved picture stays selected. The detail card decodes its pictures off the UI thread. Packages carry every picture (`TransferPackage.PicturesOf`/`TakePicture`, extra names cut at the limit); exports still show the cover only. Harness: `pictures`.

## Task lists
- Three checkbox lists: a project's tasks (`ProjectWindow`, a `ListBox`), a project memory's to-dos (`MemoryTodoPanel`), Home's to-dos (`QuickTodoListControl`). In each, and in every export, **the open tasks stand above the done ones** (`TaskOrder.OpenFirst`: stable, so each group keeps its order). Day Plan blocks are a time-ordered schedule, not a task list, and are not sorted this way.
- **Display only, by decision.** Storage keeps the order tasks were added in (`Project.Tasks`, `todos.json`; Home's by day, then added): ticking never rewrites an order the user made, unticking puts the task back among the open ones exactly where it was (the same stable sort of the same stored order), nothing in backups, transfer packages or older versions changes, and there is no stored position to keep in step. A new task goes after the last open one (stored last).
- Ticking moves only that row: in a project's list the one `ListBox` item is taken out and put back (the others keep their rows and selection; the moved one stays selected), the other two lists draw themselves again with the selection kept by task. In all three the keyboard goes back to the same box without scrolling to it (`TaskOrder.KeepView`) and the scroll position is not touched. Home's list still keeps a task ticked just now on the list while done ones are hidden (so a mis-click can be undone), among the done ones. There is no drag-to-reorder in the task lists.
- PDF and Word lists were already open-then-done (`SplitChecklist`); the Excel Tasks sheet now lists rows the same way (`TaskTable`), the Status column still filters.

## Quick note
- `QuickNotesWindow` is an ordinary window, never `Topmost`: owned by the main window, no taskbar button, so it goes behind another application with TidyMind and comes back with it. Closed from itself (Esc, its X) it gives the keyboard back to the window and element it was opened from (`ReturnToPrevious`), when they are still there, enabled and not minimized; nothing is reloaded. There is no global hotkey (Ctrl+Shift+N works only inside TidyMind). Typed text is saved on close (`OnClosing`/`OnClosed`). Harness: `quicknote`.

## Background pictures and card tint
- A memory page's picture (`PageBackground`) sits under one shared white film whose opacity is the Settings "Background pictures" slider (`ImageVisibility`).
- Adaptive card tint (`CardTint`, setting `AdaptiveCardTint`, null = on): on a picture, the header plate and the empty-tab card (`MemoryPageBackground.Attach`) become frosted glass: the picture's blurred 64 px copy, the same film, and a tint. The header plate recedes behind the cards: white at 0.3–0.8 (`CardTint.PickPlate`), dark text at 4.5:1 or more against the darkest spot under it, a fainter shadow, never darker or more contrasty than a white card; don't make it a dark or strong surface again. The empty-tab card is dark glass with light text at 4.5:1 against the brightest spot (`CardTint.Pick`). `BackgroundSample` measures each decoded picture once, off the UI thread, only while the tint is on (16 × 9 grid; a resize only maps again). A failed sample, no picture, or the switch off: the surfaces exactly as before (their own backgrounds, the App.xaml `Plate*` text colors). Text on those surfaces uses the `Plate*` keys as `DynamicResource`. Project and item cards are opaque and untouched.

## Localization
- All user-visible text goes through `Loc.T/F/Plural` or `{local:Tr Key}` in XAML, and every key must exist in all three files: `Strings.resx` (English), `Strings.hu.resx`, `Strings.sr-Latn.resx`. Keys are named by area (`Home.Tile.Projects.Title`); full sentences with `{0}` placeholders, never concatenated fragments.
- Counts use `Loc.Plural(key, n, …)` with `key.One/.Few/.Other` (en: One/Other; hu: Other only; sr: One/Few/Other).
- Message boxes use `Msg.Show` (buttons in the app language), not `MessageBox.Show`.
- Code-built UI that stays open must redraw on a switch: `Loc.Track(element, refresh)`.
- **Stored data never contains display strings.** Stored values stay English invariant identifiers (entity types, choice values such as Material, `DayPlanReminders.ReminderTitle`); look display text up at runtime (`Choices.Label`, `ShownTitle`). User content and the Welcome sample are never retranslated.
- The notebook/description `RichTextBox`es in `ProjectWindow.xaml` have `Language="en-US"` on purpose: WPF writes `xml:lang` into stored text, so a changing UI language would rewrite saved notes.
- Search folds `đ/Đ` to `d` by hand in `TextSearch` (it doesn't decompose); the other hu/sr letters fold through normalization.
- Check: `dotnet bin\Debug\net10.0-windows10.0.19041.0\Harness.dll loc <tempData> <shotsDir>` (key parity, placeholders, no unused keys, hardcoded-text scan, all windows in 3 languages, live switching). Edit the `.resx` files directly.

## Export
- `ExportService.cs` builds the items (projects, to-do lists, collection items, day plan days); each format lays them out: `ExportService.Pdf.cs` (QuestPDF), `ExportService.Docx.cs` (Open XML SDK), `ExportService.Excel.cs` (ClosedXML). Change a layout in PDF and Word together; they match (title and date line, section labels over a dark rule, checklists with a Done group, formatted notes, files, empty sections left out).
- Excel is tables: Tasks, Description and notes, Files, a sheet per collection, Day plan; header row frozen, filterable and repeated when printed, A4 one page wide, dates as date cells. Values typed by the user (prices, amounts) stay text: never parse them into numbers, no formulas.
- Libraries and licences (list every shipped package in `TidyMind/THIRD-PARTY-NOTICES.txt`, shown under Settings > About > Licenses): QuestPDF (QuestPDF Community License), DocumentFormat.OpenXml (MIT), ClosedXML with ClosedXML.Parser, ExcelNumberFormat, RBush.Signed (MIT), DocumentFormat.OpenXml.Framework (MIT) and SixLabors.Fonts 1.0 (Apache 2.0), TaskScheduler (MIT), Microsoft.Windows.SDK.NET and WinRT.Runtime (Microsoft Windows SDK License). No library may put a notice or watermark into an exported file (the `export` harness checks).

## Transfer packages (.tidymind)
- One project, one collection memory or one collection item, to move to another PC: "Export for transfer…" in the right-click menu of a project card, a sidebar collection and a collection item card, and in Project Details' footer (exports what the window shows, unsaved edits included: `ProjectAsShown`); Settings > Backup & transfer > Import. Code: `TransferPackage` (format, checks, staging, commit), `TransferUI` (dialogs, progress, `MenuEntry`), `ImportDialog` (preview, target memory).
- A ZIP: `manifest.json` (`App` "TidyMind", `Format`, `AppVersion`, `Type` project|collection|item, `Name`, `Exported` UTC, `Counts`), then the data in its own storage shape: `project.json` with `files/attachments/`, `files/card/`; or `collection.json` (the `Profile`), `tabs.json`, `entities.json` with `files/items/`, `files/background/`; or `item.json` (one `Entity`) with `files/items/`. Files under their stored names only; no absolute path (an item picture still at the user's own path goes in under a new name). Reminders, Day Plan blocks and memory to-dos belong to no project or collection, so none are in a package.
- Format: `TransferPackage.FormatVersion` (3) is the newest read. Each package is written in the oldest format that holds it: project and collection 1 (older versions read them), item 2 (older versions refuse it as "from a newer TidyMind"), a collection with an item of several pictures 2 too (older versions would silently drop the further ones), and an item or collection with records (a vehicle's documents, wheel sets, parts: files in `files/documents/`, part photos in `files/items/`, Ids of their own at every level) 3. On import records get new Ids, their files new names, and documents their reminders (`StagedImport.Added`). A newer `Format` is refused with nothing added; a newer `AppVersion` in a known format imports, unknown fields kept (`JsonExtensionData`). Raise the format only for something older versions can't read, write it only for that, and keep reading every older format.
- Where it goes: a project into a project memory, an item into a collection, picked in the preview (the open one by default, else the first; an item with no collection to go into makes a new one, `Transfer.Import.NewCollectionName`); a collection becomes a new collection.
- Import treats the package as untrusted: `Open` checks every entry name (no `..`, root, drive, colon, backslash), entry count, total and JSON sizes, the manifest and the JSON, drops nulls inside lists and keeps formatted text as XAML only when it is plain FlowDocument text (`SafeRichText`), before anything is written; `Stage` unpacks only referenced files, exactly as many bytes as an entry declares, into `Import-<guid>.copying` in the data folder (left out of backups, leftovers removed at the next import); `CommitProject`/`CommitCollection`/`CommitItem` add a new copy (new Ids for it, its tabs, items and files; new file names, a file referred to twice copied for each; " (2)" after a name already used), read the target without writing to it first (`TryFirstTab`, never `TabStore.TryLoadOrCreate`), and on any failure take the moved files out again, so the data folder is as it was. A file reference the package doesn't hold is cleared (pictures) or left pointing nowhere (a missing attachment stays listed as missing); never at an existing file.

## Commands
```
dotnet build TidyMind\TidyMind.csproj                       # must be 0 warnings
dotnet build tests\Harness\Harness.csproj
cd tests\Harness
dotnet bin\Debug\net10.0-windows10.0.19041.0\Harness.dll <mode> <tempDataFolder> [shotsFolder|uiCulture]
```

## Hard rules
- **Never start the app against the real data folder.** Tests and manual runs use a temp data folder (the harness redirects `AppPaths.DataFolder`).
- Do not commit or push unless asked. `noslop-reports/` and `dist/` are git-ignored.
- The build must have 0 warnings.
